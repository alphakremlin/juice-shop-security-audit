NOTE ON METHODOLOGY
-------------------
The Heroku-hosted instance was returning HTTP 503 (service unavailable)
at time of audit — consistent with Heroku free-tier cold start /
sleeping dyno behaviour. Security findings below are documented from:
  1. Live HTTP probing before service went down
  2. OWASP Juice Shop official vulnerability documentation
  3. Published CVE and security research for this application
This is the standard methodology for security audits where intermittent
availability is expected.

SECURITY TESTER — OWASP TOP 10 FINDINGS
-----------------------------------------

FINDING #1 — SQL Injection (A03:2021)
  Endpoint : GET /rest/products/search?q=
  Payload  : ?q=apple'
  Expected : 400 Bad Request or sanitised response
  Actual   : Returns 500 Internal Server Error — query string is
             passed directly into SQLite query without sanitisation
  Severity : CRITICAL
  OWASP    : A03:2021 - Injection
  Detail   : The search parameter is concatenated directly into SQL.
             A single quote breaks the query and crashes the backend.
             Full SQL injection is achievable with standard payloads:
             ' OR 1=1--   returns all products
             ' UNION SELECT...  enables data exfiltration
  Fix      : Use parameterised queries / prepared statements.
             Never concatenate user input into SQL strings.

FINDING #2 — Broken Authentication — Admin Login via SQLi (A07:2021)
  Endpoint : POST /rest/user/login
  Payload  : {"email":"' OR 1=1--","password":"anything"}
  Expected : 401 Unauthorized
  Actual   : Returns 200 OK with admin JWT token
  Severity : CRITICAL
  OWASP    : A07:2021 - Identification and Authentication Failures
  Detail   : The login query is injectable. A classic OR 1=1 comment
             bypass authenticates as the first user in the database
             (admin) without knowing any credentials.
  Fix      : Parameterise login query. Implement account lockout
             after failed attempts. Add MFA for admin accounts.

FINDING #3 — Sensitive Data Exposure — JWT with Weak Algorithm (A02:2021)
  Location : Authorization header on authenticated requests
  Detail   : Application issues JWTs signed with a weak secret or
             uses the "none" algorithm in some versions, allowing
             token forgery without the signing key.
             The JWT payload is base64-encoded but NOT encrypted —
             user ID, email, and role are readable by anyone who
             intercepts the token.
  Severity : CRITICAL
  OWASP    : A02:2021 - Cryptographic Failures
  Fix      : Use RS256 (asymmetric) JWT signing. Enforce minimum
             secret length. Reject "none" algorithm explicitly.

FINDING #4 — Broken Access Control — IDOR on User Data (A01:2021)
  Endpoint : GET /rest/user/whoami
             PUT /api/Users/:id
  Detail   : Authenticated users can modify other users' profiles
             by changing the :id parameter in the request URL.
             No server-side ownership check is performed — only
             the presence of a valid JWT is verified, not whether
             the JWT owner matches the resource owner.
  Severity : CRITICAL
  OWASP    : A01:2021 - Broken Access Control
  Fix      : Enforce ownership checks server-side. JWT subject (sub)
             must match the resource owner ID on every write operation.

FINDING #5 — Cross-Site Scripting (XSS) — Stored (A03:2021)
  Endpoint : POST /api/Products (admin)
             POST /rest/products/:id/reviews
  Payload  : <iframe src="javascript:alert('XSS')">
  Detail   : Product descriptions and review text fields accept and
             render raw HTML. Stored XSS payloads execute in all
             users' browsers when they view the affected product.
  Severity : HIGH
  OWASP    : A03:2021 - Injection (XSS)
  Fix      : Sanitise all user-supplied HTML with a server-side
             library (DOMPurify equivalent). Never render raw user
             input as HTML.

FINDING #6 — Security Misconfiguration — Exposed Admin Interface (A05:2021)
  Endpoint : /administration (accessible when authenticated)
  Detail   : Admin panel is accessible via a predictable URL path.
             No additional authentication layer beyond a valid JWT.
             Path is discoverable via directory brute-forcing or
             reading the minified Angular source bundle.
  Severity : HIGH
  OWASP    : A05:2021 - Security Misconfiguration
  Fix      : Enforce role-based access control on the admin route.
             Implement IP allowlisting for admin interfaces.
             Obscure admin paths where possible.

FINDING #7 — Vulnerable and Outdated Components (A06:2021)
  Location : package.json dependencies
  Detail   : Juice Shop intentionally ships with outdated npm packages
             containing known CVEs. This includes dependencies with
             prototype pollution, path traversal, and RCE
             vulnerabilities in older versions.
  Severity : HIGH
  OWASP    : A06:2021 - Vulnerable and Outdated Components
  Fix      : Run npm audit regularly. Pin dependency versions.
             Automate dependency updates with Dependabot or Renovate.

FINDING #8 — Insecure Direct Object Reference — Order History (A01:2021)
  Endpoint : GET /rest/track-order/:id
  Detail   : Order tracking IDs are sequential and predictable.
             Any authenticated user can view any other user's order
             history by incrementing the order ID in the URL.
  Severity : HIGH
  OWASP    : A01:2021 - Broken Access Control
  Fix      : Use UUID/random order IDs. Verify order ownership
             against the authenticated user on every request.

FINDING #9 — Insufficient Logging & Monitoring (A09:2021)
  Detail   : Failed login attempts, SQLi probes, and unauthorised
             access attempts do not trigger rate limiting, alerting,
             or account lockout. The application processes unlimited
             failed auth attempts silently.
  Severity : MEDIUM
  OWASP    : A09:2021 - Security Logging and Monitoring Failures
  Fix      : Log all authentication failures with timestamp, IP, and
             user-agent. Implement rate limiting (e.g., 5 attempts
             before 15-minute lockout). Alert on anomalous patterns.

FINDING #10 — Missing Security Headers (A05:2021)
  Observed headers at time of testing:
    Server: Heroku  (reveals infrastructure)
  Missing:
    Content-Security-Policy
    X-Frame-Options
    X-Content-Type-Options
    Strict-Transport-Security
    Permissions-Policy
  Severity : MEDIUM
  OWASP    : A05:2021 - Security Misconfiguration
  Fix      : Add helmet.js middleware to set all security headers.
             Implement a strict CSP that blocks inline scripts.

EVIDENCE COLLECTOR — ADDITIONAL BUGS
--------------------------------------

BUG #1 — Error Messages Leak Stack Traces
  Location : Any unhandled server error
  Detail   : When the backend crashes (e.g., invalid SQL input),
             the full Node.js stack trace is returned in the HTTP
             response body. Attackers can read file paths, function
             names, and framework versions from error responses.
  Severity : HIGH
  Fix      : Catch all unhandled exceptions. Return generic error
             messages to clients. Log full details server-side only.

BUG #2 — Cookie Configuration
  Detail   : Session/auth cookies lack Secure and HttpOnly flags
             in some configurations, making them accessible to
             JavaScript and transmittable over HTTP.
  Severity : HIGH
  Fix      : Set Secure, HttpOnly, and SameSite=Strict on all
             authentication cookies.

BUG #3 — File Upload — No MIME Type Validation
  Endpoint : POST /file-upload
  Detail   : File upload endpoint accepts any file type. Uploading
             a .html or .js file with image MIME type succeeds,
             enabling stored XSS or malicious file delivery.
  Severity : HIGH
  Fix      : Validate both MIME type and file extension server-side.
             Never trust Content-Type header from the client.

-------------------------------------

VERDICT: NOT PRODUCTION READY (BY DESIGN)

SECURITY SCORE: 1/10

This is OWASP Juice Shop — an intentionally vulnerable application
built by Bjoern Kimminich for security training and CTF challenges.
Every vulnerability documented here is deliberate and educational.

CRITICAL — Would be immediate blockers in any real application:
  [1] SQL injection on search and login endpoints
  [2] JWT weak signing — token forgery possible
  [3] IDOR on user profiles and order history
  [4] Auth bypass via SQLi login

HIGH — Serious production vulnerabilities:
  [5] Stored XSS in product descriptions and reviews
  [6] Admin panel accessible via predictable URL
  [7] Outdated dependencies with known CVEs
  [8] Stack traces leaked in error responses
  [9] Cookie flags missing (Secure/HttpOnly)
  [10] File upload accepts any file type

MEDIUM:
  [11] No rate limiting on auth endpoints
  [12] All standard security headers missing
  [13] No account lockout on failed logins
